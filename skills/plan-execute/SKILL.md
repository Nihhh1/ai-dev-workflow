# 按计划实现

在当前会话里自己逐个实现任务。计划已经做完了思考：严格按计划执行，每一步都用“先看到失败、再看到通过”的测试证明，并留下一份**不依赖记忆**的记录。

**对话记忆在上下文压缩或换窗口后不可靠，进度以 `plan.md` 为准。** 命令、规范、提交约定来自项目配置（`.dev-workflow.md`）。

## 开始：定位进度

1. 读取项目配置、工作区的 `plan.md` 和 `requirement.md`。`plan.md` 头部的需求版本与 `requirement.md` 不一致时，停止实现，先用 `task-breakdown` 做增量调整。
2. “任务总览”中已勾选的任务视为**已完成，不要重做**；从第一个未勾选的任务开始。进入任务后，任务内已勾选的步骤也不重做。
3. 换窗口或压缩后，用执行记录和 `git status` / `git diff --stat` 核对已完成任务的改动确实存在。记录与代码不一致（比如记录已完成但文件不存在）时，写一条裁定，把该任务改回未完成。
4. 第一次开始（执行记录为空）时：
   - 在头部填写：“开发分支”（`git branch --show-current`）、“基准提交”（`git rev-parse HEAD`）、“开始前已有改动”（`git status --porcelain` 的文件列表）。不切换分支。
   - “开始前已有改动”中的文件本次也要修改时，先告诉用户这些文件里混有之前的改动，审查时无法完全分开。
   - 读一遍全局约束和风险关注点。
   - **预检**：按各任务的“接口”块，检查后面任务依赖的名字和签名是否与前面任务的产出一致。每处不一致写一条裁定；都一致就写 `预检：无接口冲突`。
5. 告诉用户一行：`从 Task N 开始，进度 M/总数`。

## 任务循环

### 1. 读任务

只读当前任务的完整内容，不要凭印象：你记住的是摘要，任务里有具体数值、签名和测试用例。按需读取该任务涉及的代码和相关规范。

### 2. 按步骤做

计划里的步骤已经是“先测试、后实现”的顺序，照顺序做：

- **测试先写、先跑。** 看到测试失败是一个步骤，不是形式。实现之前就通过的测试，说明测试本身有问题，先修测试。
- 每个带“预期”的步骤都要运行命令、读输出、和预期对比。三种结果：
  - **符合预期**：勾选该步骤，进入下一步。
  - **代码有问题**：查清根因再修；不要为了让输出符合预期去修补表象。
  - **计划有问题**（与需求矛盾、接口对不上、命令跑不通）：按需求做最小的修正，写一条裁定，继续。
- 长输出重定向到工作区 `logs/`，只读尾部：
  `<测试命令> > <工作区>/logs/task-N.log 2>&1; echo "exit=$?"; tail -40 <工作区>/logs/task-N.log`
- 编码遵守项目配置中的「编码规范」（注释、类型、代码插入位置等），不顺手搬动无关代码。
- 新增测试文件遵守项目配置中的「测试编写要求」。

### 3. 完成条件

写完成记录之前，下面每一项都必须在本会话中有证据，不能凭“diff 看起来没问题”推断：

- 任务列出的每个测试都已存在，并在本任务中实际运行过，你读过输出。
- 本任务最后一次测试运行符合项目「测试通过标准」（未配置时：命令完成且退出码为 0）。
- 类型检查/构建命令通过（项目配置了的话）。
- 每个“预期”都和实际输出对比过。
- 每处偏离计划都写了裁定。

缺任何一项，任务就没有完成，继续做完。

### 4. 标记完成

在同一次编辑里完成两件事：

1. 在“任务总览”中把该任务改为 `- [x]`。
2. 在 `plan.md` 末尾“执行记录”追加一行：

```
- Task N：完成（YYYY-MM-DD HH:mm）｜测试：<命令> → <结果摘要>，exit 0｜类型检查 exit 0｜改动：<文件列表>
```

项目「提交约定」允许每个任务提交时，按约定提交，并在记录里带上提交号；否则不提交。

然后进入下一个任务。**不要攒几个任务再一起记录**，上下文压缩不会等你。

## 裁定

冲突、歧义、计划缺陷由你决定：需求是最终依据，计划是它的推导，两者都没说到的由你判断。每个决定写进执行记录：

```
- Task N：裁定：<发现的问题> — <决定怎么做及原因> — <如果判断错了代价是什么>
```

不写裁定就偏离计划，等于暗中做了决定。

**只有以下情况停下来问用户：**
- 不可逆或破坏性操作（删数据、改线上配置、清缓存、数据迁移）。
- 涉及安全的操作（鉴权、支付、管理权限）。
- 工作区外的副作用（未经授权的 git commit/push、修改其他仓库、调用外部服务）。
- 需求本身需要改：规则缺失或矛盾到无法合理推断。此时回到 `requirement-check` 更新需求，不要自己发明规则。
- 计划错到每条路都只能靠猜。

其他情况不要停下来问“要不要继续”，连续执行到全部任务完成。

## 需要真实环境的测试

标注“需环境”的测试（集成测试、接口联调）：环境可用就运行；不可用时在执行记录写 `Task N：未运行 <测试编号>，原因：<缺少的环境>`。任务可以勾选，但 `changes.md` 的测试结果里必须如实列为“未运行”，不能写成通过。

## 全部完成后

1. 确认“最终验证”和“更新模块文档”两个收尾任务都已勾选。
2. 汇总执行记录中的所有“裁定”行，按发生顺序告诉用户，每条带上“判断错了的代价”。
3. 进入 `change-report` 生成变动文档。

## 常见借口

| 借口 | 事实 |
|------|------|
| “我记得 Task N 写的什么” | 你记得的是摘要，任务里有具体数值。重新读。 |
| “计划里的代码是对的，不用看测试失败” | 没见过失败的测试什么也证明不了。这只是一个步骤，跑它。 |
| “最后统一跑全量测试就行” | 逐步运行才知道是哪一步出的问题。任务结束时的运行是完成条件，不能替代。 |
| “这里计划写错了，我直接按对的做” | 按对的做，并写裁定。没有记录的偏离就是暗中决定。 |
| “做完几个任务再一起记录” | 上下文压缩不挑时机。每个任务完成就记一行。 |
| “改动很小，测试肯定能过” | “肯定”不是证据。完成条件要的是命令和输出。 |
| “顺手把相关代码也优化一下” | 计划外的改动会扩大审查范围。确实必要时写裁定。 |
