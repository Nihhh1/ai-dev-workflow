# 变动文档

为**用户本人和后续审查者**写一份读得懂的变动说明：先讲结论，再讲细节。内容以实际代码差异为准，不照抄 plan。

**前提：** `plan.md` 的任务总览已全部勾选，否则回到 `plan-execute`。

**保存位置：** `<工作区>/changes.md`

## 第 1 步：收集事实

- 改动范围：`git diff --stat <基准提交>`（基准提交见 plan.md 头部），加上 `git status --porcelain` 中未跟踪的新文件，再排除 plan.md 头部“开始前已有改动”中的文件。被排除但本次也改过的文件，单独列为“混有开始前改动”，只描述本次改的部分。
- 逐个读关键文件的差异，弄清实际实现，而不是计划里的设想。
- plan.md 执行记录中的“裁定”行和“未运行”行。
- 最终验证的测试命令和结果。

## 写作要求

- 写给没参与开发的人看：先写结果，少用开发过程中临时起的叫法。
- 文件引用使用仓库相对路径，需要时带行号。
- 测试结果只写本会话中实际运行过的命令和结果；没运行的写“未运行”和原因，不能写成通过。
- 不复述代码：实现逻辑讲“做什么、为什么”，不是逐行翻译。

## 审查后同步

审查后有修复的话，更新本文档中受影响的“改动清单”“实现逻辑”“测试结果”，并追加：

```markdown
## 审查修复
| 问题 | 处理 | 测试 |
|------|------|------|
```

## 交付

写完后告诉用户：文档路径、一句话总结、测试是否全部通过（有未运行的要说明）、最需要关注的一条风险。然后进入审查环节。
