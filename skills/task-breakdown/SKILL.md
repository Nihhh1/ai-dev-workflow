# 任务与测试拆分

把计划写给一个**没看过这个仓库、也没看过需求**的开发者：他能写出地道的代码，但不知道你做了哪些决定——改哪些文件、用什么名字和签名、需求里的哪些具体数值、哪些测试能证明任务完成。plan 要写的就是这些决定。

计划最主要的作用是**让开发可以中断**：每个任务都是独立、可验证的一小块；上下文快满时，新窗口只读 `plan.md` 和 `requirement.md` 就能接着做下一个任务。

**保存位置：** `<工作区>/plan.md`（与 `requirement.md` 同目录）。

**前提：** `requirement.md` 状态为“已确认”，否则回到 `requirement-check`。项目配置（`.dev-workflow.md`）已读取。

## 第 1 步：读上下文

- `requirement.md` 全文，记下规则编号 R*、验收标准 AC*。
- 涉及模块的模块文档，以及项目配置中「编码规范」「框架与领域规范」里与本需求相关的部分。
- 同类功能的现有实现，**沿用既有模式**，不另起炉灶。

## 第 2 步：规模检查

需求覆盖多个互相独立的子系统时，建议拆成多份 plan（每份能单独交付、单独测试），先和用户确认拆法。

## 第 3 步：文件结构

定义任务前，先列出要新建或修改的文件以及各自的职责，拆分决策在这里定下来。

- 按项目配置「目录结构」和现有代码的分层放置文件。
- 每个文件职责单一、边界清晰；一起变化的文件放在同一个任务里。
- 别漏掉横切登记点：依赖注入注册、路由/协议 ID 注册、缓存 key 定义、清理逻辑、权限配置等（项目配置中可列出）。
- 已有代码习惯用大文件时不擅自重构；但要修改的文件已经难以维护时，可以在计划里包含拆分。

## 第 4 步：划分任务

一个任务是**带有自己测试循环、值得单独审查的最小单元**。

- 搭建、配置、注册、文档等步骤并入需要它们的那个任务，不单独成任务。
- 只有当审查者可能“通过这个任务、驳回相邻任务”时才拆开。
- 每个任务结束时都有可以独立测试的交付物。
- 推荐顺序：基础定义（类型/配置解析/数据模型/数据访问）→ 按功能点纵向切片（每片从业务规则到对外接口）→ 横切登记 → 性能与兼容专项（需要时）→ 最终验证 → 更新模块文档。

## 第 5 步：测试矩阵

每条测试有编号，并写明对应的规则/验收编号和所属任务。必须覆盖以下类型；不适用的写“不涉及：<原因>”，不要直接省略。

| 类型 | 编号前缀 | 要求 |
|------|----------|------|
| 功能测试 | F | 每条验收标准 AC 至少一条；正常路径的输入、输出和持久化结果都要断言 |
| 边界与异常 | B | 时间边界（开始/结束/重置时刻前后）、数量上限、配置缺失或非法、参数非法、每个错误码 |
| 并发与幂等 | C | 重复请求、同一用户并发、多用户抢同一资源、重试；断言资源不重复发放、计数不超限 |
| 性能测试 | P | 见下方“性能测试怎么写” |
| 兼容测试 | M | 旧数据缺字段时的默认值、发布期间新旧版本共存时接口与缓存数据可读、配置热更后进行中数据的处理 |
| 接口联调 | I | 可选，需要真实环境；按项目配置中的「接口联调」方式执行，在 plan 中标注“需环境” |

### 性能测试怎么写

按需求的“性能与规模”选择，至少给热点接口和批量处理各定一个指标：

1. **调用次数预算**（单元测试，最常用）：用替身对象记录数据库/缓存调用次数，断言单次请求的查询和往返次数不超过预算，并且不随列表长度线性增长（防 N+1）。示例：`查询信息接口：数据库查询 ≤ 1 次，缓存往返 ≤ 2 次，与奖励档位数量无关`。
2. **耗时预算**（单元测试）：测纯计算或批量处理，按需求给的规模构造数据。示例：`1 万名用户排行结算 < 200ms`。预算留出余量，避免机器波动导致误报；按测试框架要求设置超时。
3. **并发正确性与吞吐**（集成测试，需要真实数据库/缓存）：并发发起 N 个请求，断言结果一致、总耗时在预算内。标注“需环境”。
4. **基准脚本**（可选）：需要在几种实现之间选择时，写独立的基准脚本对比，并在项目脚本里登记运行命令。
5. **线上观察点**：热点路径加耗时埋点或指标（使用项目配置「性能工具」中列出的工具），作为上线后的验证手段写进计划。

另外检查数据规模：单条记录是否会随时间无限增长、缓存 key 是否设置了过期时间、大 key 风险、新查询条件是否有索引。

## 第 6 步：写 plan.md

### 文档头部

```markdown
# <需求名称> 开发计划

> 执行方式：使用 `plan-execute` 技能逐个任务实现。任务完成后在“任务总览”中勾选；中断后从第一个未勾选任务继续。

- 需求文档：requirement.md（需求版本：v1）
- 目标：<一句话说明要做成什么>
- 方案：<2～3 句说明整体实现思路和关键取舍>
- 开发分支：<执行阶段第一次开始时的当前分支>
- 基准提交：<开始开发时 `git rev-parse HEAD` 的结果，执行阶段第一次开始时填写>
- 开始前已有改动：<开始开发时 `git status --porcelain` 列出的文件；没有写“无”。变动文档和审查会排除这些文件>

## 全局约束
> 编码规范、测试命令与通过标准、发布约束、提交约定遵守仓库规范文件（AGENTS.md/CLAUDE.md）与 `.dev-workflow.md`，此处不重复。

<每条一行，所有任务都隐含遵守。只写项目规范之外、本需求特有的约束；仓库规范文件与项目配置中已有的内容不要摘抄>
- <从需求中抄录的全局数值，例如周期 14 天、每日 5 点重置>
- <本需求统一使用的取值或约定，例如沿用的错误码、固定的枚举编号>

## 风险关注点
<需求隐含、但最容易出问题的 5 个输入或故障场景，每条一行：场景 + 合理预期行为，最可能出问题的排在前面。每一条都要在负责的任务里补上对应测试，并注明测试编号。>

## 任务总览
- [ ] Task 1：<名称>（R1, R2）
- [ ] Task 2：<名称>（R3）
- [ ] Task N-1：最终验证
- [ ] Task N：更新模块文档

## 测试矩阵
| 编号 | 类型 | 对应 | 用例 | 所属任务 | 测试文件 |
|------|------|------|------|----------|----------|
| F1 | 功能 | AC1/R1 | ... | Task 2 | ... |
| P1 | 性能 | R5 | 查询接口数据库查询 ≤ 1 次 | Task 2 | ... |

---
```

### 任务结构

````markdown
### Task N：<名称>

**对应规则：** R1, R2 ｜ **测试：** F1, B2, P1

**文件：**
- 新建：`<精确路径>`
- 修改：`<精确路径>`（<插入位置，例如某个命名空间末尾>）
- 测试：`<精确路径>`

**接口：**
- 依赖：<使用前面任务产出的哪些名字和签名，写完整签名>
- 产出：<后面任务依赖的名字、参数和返回类型。执行者只看自己的任务，这里是他知道相邻任务用什么名字的唯一途径>

- [ ] 步骤 1：编写失败的测试

```<语言>
// 测试名对应测试编号；只写关键断言，带上需求中的具体数值
```

- [ ] 步骤 2：运行测试，确认失败
  运行：<项目配置「单测命令」，替换为本任务的测试文件>
  预期：失败，原因是 `<函数> 未定义` 或断言不满足

- [ ] 步骤 3：实现 `<方法签名>`（位于 `<文件>`）
  只在签名和测试无法确定做法时写一行思路（用哪个已有工具、什么数据结构）；只有签名和测试决定不了的算法才给代码。

- [ ] 步骤 4：运行测试，确认通过
  运行：同步骤 2
  预期：全部通过，符合测试通过标准

- [ ] 步骤 5：类型检查/构建
  运行：<项目配置「类型检查/构建命令」>
  预期：无错误
````

项目配置中没有类型检查命令时去掉步骤 5；有 lint 命令时追加 lint 步骤。

### 固定的收尾任务

- **最终验证**：运行本需求涉及的全部测试 + 类型检查/构建；需要时运行项目配置中的全量测试命令做回归；逐条核对测试矩阵，每个编号都要有实际运行过的测试（或明确标注“未运行”及原因）。
- **更新模块文档**：按项目配置「模块文档」的位置和技能，更新或新建 `requirement.md`“涉及模块”中每个模块的文档（任务里写出具体路径），只描述功能当前的样子：核心规则、数据结构、关键流程、容易踩坑的特殊规则。删除失效内容，而不是补充“不再……”。

## 每一步写什么

一步写到执行者只能写出**一种合理实现**为止：要无歧义，不必面面俱到。

- **测试步骤**：测试名和断言代码，带上需求里的具体数值。
- **代码步骤**：完整签名（名称、参数、返回类型）、所在文件、需求固定的数值。函数体由执行者写；只有签名和测试决定不了的算法才给代码。
- **验证步骤**：要运行的命令，以及什么输出算通过。
- **引用其他任务**：通过那个任务的“接口”块说明用什么，不重复它的代码。

计划比它描述的代码还长，说明把代码写进了计划。反过来，“待定”“处理边界情况”“添加适当校验”“为以上功能写测试”、引用了没有任何任务定义的类型或函数，都是没做决定。自检会抓出这两类问题。

## 第 7 步：自检

写完后对照需求重新检查，有问题直接改，不需要再复查一遍：

1. **需求覆盖**：每条 R*、AC* 都能指到一个任务和至少一条测试。缺了就补任务。
2. **测试矩阵**：六种测试类型都有用例或写明“不涉及”的原因；性能至少覆盖热点接口和批量处理。
3. **步骤检查**：每一步只能写出一种合理实现；没做决定的行、把签名和测试已经能确定的函数体照抄进来的行，都要改掉。
4. **类型一致**：后面任务用到的类型、方法签名、字段名与前面任务定义的一致。Task 3 叫 `clearLayers()`、Task 7 叫 `clearFullLayers()` 就是 bug。
5. **风险关注点**：每条都已在负责的任务中补了测试。
6. **比例**：计划长度明显超过需求时，用签名、测试名和断言替换代码块。

## 第 8 步：交付

告诉用户 plan 的路径、任务数量、测试数量（按类型），以及你认为风险最高的一两个任务。请用户审阅，确认后进入 `plan-execute`。

## 需求变更后的增量调整

`requirement.md` 版本升高时：
- 把头部的需求版本更新为新版本。
- 只改受影响的任务和测试；已完成但需要返工的任务改回 `- [ ]`，并在执行记录追加 `变更：v<旧>→v<新>，Task N 返工，原因：<规则编号与变化>`。
- 重新执行第 7 步自检中的 1、2、4 项。
