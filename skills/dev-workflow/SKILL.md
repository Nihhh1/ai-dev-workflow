# 需求开发总流程

本技能只负责**编排与断点续做**，每个环节的具体做法由对应技能决定。哪一环不适合，只替换那一个技能，不改整体流程。

```
① 需求完整性检查   requirement-check（缺口交给 grilling 追问）
        │  产出：requirement.md（状态：已确认）
        ▼
② 任务与测试拆分   task-breakdown
        │  产出：plan.md（任务 + 测试矩阵 + 执行记录）
        ▼
③ 按文档逐个实现   plan-execute（每完成一个任务在 plan.md 打勾）
        │  产出：代码 + 测试 + 模块文档更新
        ▼
④ 生成变动文档     change-report
        │  产出：changes.md
        ▼
⑤ AI 代码审查      配置中的「审查技能」（默认 ai-code-review-enhanced）
        │  产出：review.md；必须修正的问题回到 ③ 修复
        ▼
⑥ 归档清理         模块文档已在 ③ 更新；经用户确认后删除工作区
```

## 第 0 步：读取项目配置

所有项目相关信息（命令、目录、规范、模块文档位置、提交约定、部署约束）都来自仓库根目录的 **`.dev-workflow.md`**。本流程的其他技能提到“项目配置”时，指的都是这份文件。

- 文件存在：读取全文，后续环节按它执行。
- 文件不存在：
  1. 从仓库中查清事实：`AGENTS.md`/`CLAUDE.md`/`CONTRIBUTING.md`、包管理器和 `package.json`（或 `go.mod`、`pom.xml`、`pyproject.toml` 等）中的测试与构建脚本、测试目录结构、默认分支、现有模块文档的位置。
  2. 按本技能目录下 `templates/dev-workflow.config.md` 的格式起草一份配置，查不到的项标注“待确认”。
  3. 把草稿发给用户确认，确认后写入仓库根目录。配置文件固定放在仓库根目录，不放到其他位置，否则下次找不到；用户不想提交它时，把 `.dev-workflow.md` 加入 `.git/info/exclude`（只在本地忽略，不改 `.gitignore`）。

项目配置与本技能冲突时，**以项目配置为准**。

### 文档位置一览

| 文档 | 位置 | 由谁决定 |
|------|------|----------|
| 项目配置 | 仓库根目录 `.dev-workflow.md` | 固定 |
| 工作区 | `<工作区目录>/<YYYY-MM-DD>-<feature>/` | 配置「基本 → 工作区目录」，默认 `docs/dev` |
| 原始需求 | `<工作区>/source/` | 固定 |
| 需求文档 | `<工作区>/requirement.md` | 固定 |
| 拆分文档 | `<工作区>/plan.md` | 固定 |
| 变动文档、审查结果 | `<工作区>/changes.md`、`<工作区>/review.md` | 固定 |
| 模块文档（开发前查看、归档时更新） | 配置「模块文档 → 位置」，用 `requirement.md` 头部“涉及模块”的模块名代入 | 配置；未配置时默认 `docs/modules/<模块>.md`，第一次使用时向用户确认并写回配置 |

## 工作区

每个需求一个工作区：`<工作区目录>/<YYYY-MM-DD>-<feature>/`。工作区目录取自项目配置（默认 `docs/dev`），`<feature>` 用短横线英文名。

工作区只服务于本次开发，归档后删除。改动历史交给 git 提交和 MR/PR，不另存历史文档。建议把工作区目录加入 `.gitignore`。

| 文件 | 写入环节 | 作用 |
|------|----------|------|
| `source/` | ① | 原始需求文档（docx/xlsx/pdf 等）以及转换出的 `.md` |
| `requirement.md` | ① | 本次需求的唯一依据，开发中途改需求只改这里 |
| `plan.md` | ②③ | 任务拆分、测试矩阵、复选框进度、执行记录（裁定、偏差、测试结果） |
| `logs/` | ③ | 长测试输出重定向到这里，只读尾部，避免撑爆上下文 |
| `changes.md` | ④ | 变动文档：改了什么、实现逻辑、测试结果、风险 |
| `review.md` | ⑤ | 审查报告与每条问题的处理结论 |

## 开始或继续：先判断当前阶段

每次被调用（包括新窗口、上下文压缩后），先读项目配置、定位工作区，再按下表从上往下找第一个不满足的条件，从那一步开始。**不要凭对话记忆判断进度，以文件为准。**

1. 用户指定了工作区或需求名 → 用它；否则列出工作区目录下的子目录：只有一个就用它，多个让用户选，没有就新建。
2. 判断阶段：

| 条件 | 进入 |
|------|------|
| 没有 `requirement.md`，或其状态不是“已确认” | ① requirement-check |
| 没有 `plan.md`，或 `plan.md` 头部的需求版本与 `requirement.md` 不一致 | ② task-breakdown（版本不一致时做增量调整） |
| `plan.md` 的“任务总览”中仍有未勾选的 `- [ ] Task` | ③ plan-execute，从第一个未勾选任务继续 |
| 没有 `changes.md` | ④ change-report |
| 没有 `review.md` | ⑤ 审查 |
| `review.md` 中有“必须修正”且处理结论为空的问题 | 回到 ③ 修复，再更新 `changes.md` 和 `review.md` |
| 以上都满足 | ⑥ 归档清理 |

3. 开始前用一行告诉用户：`工作区：<路径>，当前阶段：<阶段>，进度：<N/M 任务>`。
4. 只调用当前阶段对应的那一个技能；进入下一阶段时再调用下一个，不要提前加载后续环节的技能。

## 各环节衔接

### ① → ②
`requirement.md` 状态为“已确认”才能拆分。用户只发来文档、没说已确认时，先给出完整性检查结论和待确认项，等用户确认。

### ② → ③
拆分完成后把 `plan.md` 交给用户审阅，用户确认后再开始实现；用户明确说“直接做”时可以跳过等待。

### ③ 过程中需求变化
回到 ①：先改 `requirement.md`（版本号 +1、写变更记录），再回到 ② 调整 `plan.md` 中受影响的任务（已完成任务需要返工的改回 `- [ ]`，并在执行记录写原因），然后继续 ③。**不允许只改代码不改文档。**

### ③ → ④
`plan.md` 全部任务已勾选，并且最终验证（项目配置中的类型检查/构建命令 + 本需求全部测试）在本会话中实际运行通过，才能生成变动文档。

### ④ → ⑤
调用项目配置中的「审查技能」（默认 `ai-code-review-enhanced`），并直接提供以下信息，避免它再询问：
- 比较基准：`plan.md` 头部的“基准提交”（本需求开始开发时的 HEAD）。审查范围是 `git diff <基准提交>` 加上未跟踪的新文件，再**排除**头部“开始前已有改动”中列出的文件（这些文件本次也改过的，在报告中注明“混有开始前的改动”）。只有整个分支都属于本需求时，才改用 `git merge-base <默认分支> HEAD`。
- 流程不限定分支：在当前所在的任何分支上开发，不切换、不新建分支，除非用户要求。
- 需求来源：`requirement.md` 的路径。
- 规范来源：项目配置中的「编码规范」和「框架与领域规范」。

审查结果写入 `review.md`。每条问题都要有处理结论：`已修复（对应测试）`、`不修复（原因）` 或 `待用户确认`。必须修正的问题回到 ③：在 `plan.md` 末尾追加修复任务，修完后同步 `changes.md`。

### ⑥ 归档清理
- 核对 plan 的最后一个任务已经按项目配置中的「模块文档」约定更新了文档，并且文档只描述功能当前的样子。
- 把 `changes.md` 的摘要提供给用户，作为提交信息或 MR/PR 描述的素材。提交遵循项目配置中的「提交约定」；未配置时，未经用户明确授权不执行 `git add`/`git commit`/`git push`。
- **征得用户确认后**删除整个工作区目录。用户想保留就不删。

## 规模分级：可以跳过的环节

| 改动规模 | 示例 | 走哪些环节 |
|----------|------|------------|
| 小 | 单点 bug、改一处配置读取、文案/错误码 | 直接改 + 测试；模块规则有变化时更新模块文档；不建工作区 |
| 中 | 已有功能迭代，涉及 1～2 个模块，接口变化少 | ① 简化检查 → ② → ③ → ④ → ⑤ |
| 大 | 新功能、新接口/协议、新数据表、跨模块、涉及资金/资产/结算 | 全流程，不得跳过 |

规模不确定时按大一级处理，并告诉用户你的判断。项目配置可以覆盖这张表。

## 约束

- 全程遵守项目配置中的「编码规范」。
- 测试结论遵守项目配置中的「测试通过标准」；未配置时，命令完成且退出码为 0 才算通过，只看到“passing”不算。
- 每个环节结束时，用一两句话告诉用户产出在哪里、下一步是什么。
